# Symptom / ask
Operator (workspace 00045): a "Would you rather?" game in the chat's ... menu. Each round asks both people what THEY would rather and what they think the OTHER would pick; results show only after BOTH press Reveal. 2,000+ questions across food, travel, date nights, interiors and more, each option with a picture generated on Hub's GPU at the moment the round is shown, never ahead of time.

# Decided
- **One table per round, anchored to a message** (schema v15 `wyr_rounds`, PK = `anchor_message_seq`, `ON DELETE CASCADE`) — the drawings precedent (decisions/00164): the table is the message-kind marker, no `messages` column, and an older blue/green process that deletes a message still removes the round. There is deliberately NO separate played-questions table (an early draft had `wyr_used`; the audit showed it kept a dated record that survived per-message delete and an older process's wipe): the repeat guard is derived from the rounds that exist, so deleting a round forgets it. Random pick of unplayed; when the bank is exhausted the pool resets. Wipe clears the rounds explicitly.
- **State machine** `voting -> answering -> revealing -> revealed`, or `skipped` from `voting` (any skip vote) or by a newer round superseding it. The creator is player 1 and has already voted `play`; the first other voter is player 2; a third is refused (`full`/`bad_state`). Every mutation is idempotent (a retry after a dropped response never flips anything) and announced via the existing `message_updated` event — no new event type, no `events` rebuild.
- **The game rule is enforced on the server**: `wyr_view_json` never includes the other player's pick/guess until `state == "revealed"`, and `Message.wyr` carries only `{state, rev}`. The chat's trust model is unchanged (anyone unlocked can read anything; the filter keeps the game fun, it is not a secret-keeping boundary).
- **Question bank is static repo content** (`wixy_server/livechat/wyr_questions.json`, 2,352 questions after dedupe from 2,400 written by ten Luna writers, 10 categories; ids `qNNNN` permanent, append-only). It reveals nothing about anyone so wipe never touches it. Dedupe: exact normalised option pair (order-insensitive), then token-Jaccard >= 0.72 near-duplicates.
- **Pictures are ordinary photo attachments** painted on demand: `POST /wyr` commits the round, then a background job (`wyr_game.generate_round_images`) probes ComfyUI, renders both options in ONE submission (two sampling chains sharing loaded models), stages each PNG as `uploads/<id>/assembled` and attaches both via `create_wyr_image_attachments` (uploads + attachment + link in one transaction, so the media queue can never claim an attachment with no home). Signed URLs, renditions, quota and delete/wipe erasure are all inherited. A generator failure or a missing `WIXY_COMFY_URL` leaves a text-only round; the game never 5xxs for it. `wyr_rounds.images` (`none|pending|done|failed`) is the job's state: every exit of the job ends `pending` and bumps the round, so the card never waits for pictures that are not coming; startup fails any stale `pending`.
- **ComfyUI keeps what it renders** (audit finding, high): `SaveImage` writes into ComfyUI's output folder and the prompt stays in `/history`, neither reachable by delete/wipe. Fix: each run deletes its own history entry and `wyr_*` output files, cancels a run it abandons (`/queue` delete + `/interrupt` with the prompt id), a startup sweep removes `wyr_*` files older than the generation budget, and `WIXY_COMFY_OUTPUT_DIR` (the folder ComfyUI writes to) is REQUIRED for pictures — unset means disabled (fail-closed). The configured folder is VERIFIED, not trusted: ComfyUI reports its launch arguments in `/system_stats`, and a mismatch with `WIXY_COMFY_OUTPUT_DIR` (or no `--output-directory` at all) disables pictures before any render; a build that reports no arguments is caught by a post-run check that the reported files are in the configured folder (then sticky-disabled). Any exit of a run other than ComfyUI reporting it finished cancels it. A periodic sweep (every 10 min, and at startup) removes `wyr_*` files older than the generation budget and the history entries whose files are gone or stale — the backstop for a run orphaned by a killed process. Residual: files exist for seconds (up to ~25 min if the process dies mid-run) and are unlinked, not scrubbed.
- **Single-flight picture jobs** (audit, medium): `CapacityLimiter(1)`, and the round is re-checked (exists, not skipped) before GPU work and before attaching.
- **Answers filter bound to the sign-in** (audit, low): the CF Access email that took a slot is stored; naming that player under a different verified email is a stranger/`not_player`. Unknown email on either side falls back to the name.
- **Model**: Krea 2 Turbo NVFP4 on ComfyUI (Hall topic 00072's everyday pick), 8 steps, 1024x1024; Boogu Turbo selectable via `WIXY_WYR_IMAGE_MODEL`. Measured live 2026-10-16: a pair rendered in ~46 s including cold model load on the shared card.
- **Release notes**: the game's commits carry `Release-note: General bug fixes and improvements.` (R14a-style discretion in a hidden chat).

# Why not
- A `messages` column / `ALTER` or a new event type: forces the events-table rebuild the drawings design deliberately avoided.
- Pre-generating pictures: the operator wants them painted when the round is shown; 2,352 x 2 pictures would also be pure storage cost.
- Sending the full round to both clients and hiding client-side: a client cannot be trusted to hide what the server sent it.

# Watch for
- The image job holds a worker thread for the whole generation (up to the 300 s budget); a second round started meanwhile simply queues behind it on ComfyUI.
- Staged PNGs live in `server/wyr-tmp/` during a run and are cleared at every app start (Inv 54) — they are chat content.
- Bank ids are permanent: never renumber, only append.
