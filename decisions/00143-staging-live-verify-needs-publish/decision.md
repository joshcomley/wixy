# Live-verifying WP1-WP5 on `ca.cinnamons.uk` requires a Publish — engine deploy alone is not enough

## Symptom

At the end of the search-indexing mission's implementation phase (WP1-WP5 all merged to
`main` in both the wixy engine repo and `cottage-aesthetics-preview`), checked whether WP1's
noindex-observable fix (`decisions/00135`, wixy PR #203) was actually live on `ca.cinnamons.uk`
before declaring the mission done. It was not:

```
curl -s -i "https://ca.cinnamons.uk/robots.txt?cachebust=<ts>"
cf-cache-status: MISS   (genuinely fresh from origin, not a stale CDN edge cache)
User-agent: *
Disallow: /             <- the OLD, pre-WP1 crawl-block, not the new crawl-allow
```

The `etag`/`last-modified` on that response matched the timestamp of `wixy: publish v65`
(the last owner Publish, per the brief's own "Environment" section) — predating every PR this
mission shipped.

## Root cause

Two independent things happen on a wixy engine merge to `main`, and it's easy to conflate them:

1. **Slots deploys the engine CODE** (`docs/ai/runbook.md`'s "Deploy = merge to main"):
   within ~30s, the running `Wixy` service (`ca.cinnamons.uk`) is running the new
   `wixy_server`/`builder` code. This part genuinely is automatic and needs no owner action.
2. **The static build ARTIFACTS** (`robots.txt`, `sitemap.xml`, every rendered page's
   `<meta name="robots">`, JSON-LD, `<img>` intrinsic dimensions, the `.creds`/`.tgrid`/etc.
   CSS a template change might depend on) are only regenerated by `publisher.py:run_publish`'s
   `build_site` step (`docs/ai/publish-pipeline.md` step 4 "building/verifying"), which runs
   **only** on `POST /api/admin/publish` — i.e. only when Purdi presses Publish in Wixy. A
   Slots-triggered process restart does **not** call `run_publish`; `bootstrap_if_needed`
   (`wixy_server/app.py`'s lifespan) is explicitly documented as "a no-op once `live.json`
   exists (every startup after the first)".

So: new engine code is live and CORRECT the instant it runs against fresh input, but the actual
bytes served at `ca.cinnamons.uk/robots.txt` (and every other build artifact) are frozen at
whatever they were computed as during the last Publish, until the next one. This is the exact
same "code deployed, content not yet published" split that WP4-4B's own audit already
identified for a single page's CSS (`routes_preview.py`'s dynamic `render_page` picking up new
code immediately vs. `theme.css` only regenerating on Publish, decisions/00140) — this entry
generalizes it: it's true of **every** static build artifact for the **whole site**, not just
one CSS file, and it's true even for the plain non-admin `ca.cinnamons.uk` routes, not only
the public GitHub Pages domain.

## What this means for the mission

**Nothing shipped in WP1-WP5 is live-verifiable — on staging OR the public domain — until the
next owner Publish.** This is not specific to the site-repo content packages (WP2/WP3/WP4/WP5,
which obviously needed Publish to reach GitHub Pages); it's equally true of WP1's noindex fix,
which is pure wixy-engine code and was assumed to be "live the moment Slots deploys it" — that
assumption was wrong, checked directly, not just corrected after the fact.

The one thing that IS live immediately on an engine deploy, no Publish needed: **request-time**
behavior that isn't baked into a static build — e.g. Inv 37's `X-Robots-Tag: noindex` response
header on `/images/*` and the version endpoints (computed per-request by middleware, not
written to disk at build time), and the admin preview's dynamic `render_page` calls
(`routes_preview.py`). Anything that lands in `builds/<sha>/` on disk (robots.txt, sitemap.xml,
every page's rendered HTML including its `<head>` noindex/canonical/JSON-LD, image dimension
attributes) does not.

## What to watch for

- Before declaring ANY future work package "live-verified," check whether the specific thing
  being verified is a build-time artifact (needs Publish) or a request-time behavior (doesn't).
  Don't assume "the engine PR merged and Slots deployed it" is sufficient evidence.
- The brief's own "Definition of done" ("packages 1-4 are merged, deployed through their normal
  mechanisms, and live-verified") is therefore not achievable by the agent lane alone — the
  "deployed"/"live-verified" clause has a hard dependency on the owner's Publish action for
  every package in this mission, not just the content-heavy ones.
- Once Purdi publishes: re-run WP0's exact baseline probes (robots.txt, sitemap.xml, structured
  data, legacy redirects on GitHub Pages, a fresh Lighthouse median-of-3) against BOTH
  `ca.cinnamons.uk` and `cottageaesthetics.co.uk`, and record the results — this is the
  concrete, ready-to-run follow-up the moment the owner-gated step clears.
