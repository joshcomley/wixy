# Cookout twists — independent Kimi review

Reviewed `09a-cookout-twists.md` in full against the core spec, schema v21 implementation, runner/picture fencing, admin client, and panel ruling. **0 critical, 5 high.** Only critical/high findings are included.

## H1 — Secret stars are revealed while they are still mutable when the cloche is also enabled

- **Severity:** High
- **Section/line:** Addendum §1.4 lines 175–199; §1.5 lines 205–217, especially 207–214; §1.9 line 324; §4.3 line 838.
- **Problem:** The addendum defines `starsRevealed` as soon as the round is finished and both star ids are set, and calls that “the moment the stars lock.” But it also allows `POST /star` changes throughout `concepts == 'none'`, and says stars lock only when concepts leave `'none'`. With the wildcard gate still unanswered, both stars can therefore be revealed while either player can still change them. Reveal and lock are not the same transition as the contract claims.
- **Failure scenario:** Enable stars and cloche. Both players star during the draft (or after Turn 10). Turn 10 reveals the basket and offers the cloche, while concepts remain `'none'`. Both star ids are now visible to the partner. Either player then posts a different own pick; it is accepted because the cloche has kept concepts at `'none'`, so the supposedly revealed/locked secret answer changes before the chef starts.
- **Exact fix:** Use one transition for reveal and lock. Preserve the stated edit window by changing `starsRevealed` to require the **whole chef gate to have cleared** (`state == 'finished'`, both ids set, and `concepts != 'none'`). Until then expose only `mine` and `partnerChosen`; once the last gate answer moves concepts to `pending`/`unavailable`, reveal both and reject every further star change with `409 bad_state`. Add a stars+cloche test proving that both-set-before-cloche is still secret and mutable, and that answering the cloche atomically reveals and locks both stars.

## H2 — Archiving a generation can publish a single secret dinner vote forever

- **Severity:** High
- **Section/line:** Addendum §1.6 lines 243–245 and 249–255; §1.7 lines 273–281; §4.3 lines 812–815 versus the live-vote redaction at 839–840.
- **Problem:** A swap archives raw `vote1`/`vote2`, including a one-sided vote, and archived generations are read-only. The view gives each archived generation a `votes` object but specifies the secrecy/redaction rule only for the current generation’s top-level `vote`. Nothing says to suppress an archived vote until both players voted. Since no more votes can be cast on an archived generation, a one-sided vote can never reach its legitimate reveal moment.
- **Failure scenario:** In either Open or Blind mode, Player 1 secretly votes for concept `b`; Player 2 has not voted. Before Player 2 votes, the players complete a rescue swap. Generation 1 now contains `vote1='b', vote2=NULL`. If the specified archived `votes` map is serialized as stored, Player 2’s Earlier dishes response reveals Player 1’s secret `b`. It remains visible forever, contrary to §1.7’s “before the reveal a viewer sees only their own vote and `partnerVoted`.”
- **Exact fix:** Apply the vote reveal predicate independently to every archived generation: `votes` and `match` may be non-null only when **both** archived votes are non-null. For an incomplete archived vote, return `votes: null, match: null` to the partner and non-players (and, with the current shape, to every viewer); never serialize the raw single slot. Keep `dinnerPick` false unless both votes exist and match. Add two-player tests for a swap after only one vote, asserting that the partner’s response and DOM contain no voted concept id, plus a both-voted archive that does reveal the result.

## H3 — Recipe retry bypasses the proposed-swap freeze and blocks the swap

- **Severity:** High
- **Section/line:** Addendum §1.6 lines 228–262, especially the pending-recipe guard at 229–232 and “no new recipe job can start” at 260–262; §2.3 lines 436–441. Core `routes_livechat_cookout.py:541-570` and `store.py:4229-4251` expose a separate recipe-retry path.
- **Problem:** The proposed state refuses **Bank this**, but the existing `/concepts/{id}/recipe/retry` transition is not refused. A failed or unavailable recipe is allowed during proposal (only `pending` blocks it), and retry changes that row to `pending` and spawns a job. This contradicts the stated reason for the freeze: no new recipe job may start against dishes about to be archived.
- **Failure scenario:** Generation 1 is ready and recipe `a` is `failed`. Player 1 proposes a swap. While it is proposed, Player 2 presses the still-valid “Try again” on recipe `a`; the store makes it `pending` and the route starts the runner. Every swap choice now returns `409 recipe_pending` until that recipe finishes or times out. The choose-time guard prevents mid-job archival, but the retry has nevertheless started the forbidden job and unexpectedly holds the rescue swap hostage.
- **Exact fix:** In `retry_cookout_recipe`’s own write transaction, reject `swap_state == 'proposed'` with `CookoutBadStateError` before changing the recipe; the route must not start a runner on that refusal. Disable the recipe-retry controls as well as Bank while proposed. Add `propose -> retry` coverage proving no pending row/job appears, and a two-connection retry/choose race proving that no pending recipe can appear in an archived generation.

## H4 — The photo chooser and photo linker select different attachments from multi-photo messages

- **Severity:** High
- **Section/line:** Addendum §1.8 lines 295–308; §4.2 lines 763–767; Appendix A.2 line 1375. The implemented attachment model is ordinal-based (`models.py:100-106`), so one ordinary message can carry several photos.
- **Problem:** `GET /photos` is specified as a list of ready **photo attachments**, each with only `messageSeq` and its `picture`. The link request then identifies only the message, and the server links its lowest-ordinal photo regardless of readiness. A chooser entry therefore does not identify the attachment the linker will store. The readiness rules also disagree: the list can offer a ready second photo while the linker selects a failed first one, which the view then refuses to display.
- **Failure scenario:** A mini-chat message has ready photos at ordinals 0 and 1. The chooser shows two thumbnails with the same `messageSeq`; tapping the second still links ordinal 0, so the user gets the other picture. If ordinal 0 failed and ordinal 1 is ready, the chooser shows only ordinal 1, but linking stores failed ordinal 0 and “Our plate” remains empty despite the user selecting a valid ready photo.
- **Exact fix:** Keep the existing `messageSeq` request but make the whole contract message-keyed and readiness-consistent: return at most one chooser entry per message, using its **lowest-ordinal ready** photo, and have `link_cookout_photo` select that same attachment. Reject a message with no ready photo. (Adding an `attachmentId` to both the chooser item and link request would also resolve it, but is unnecessary.) Add tests with two ready photos and with failed-first/ready-second, asserting that the displayed thumbnail’s attachment id is exactly the stored `photo_attachment_id`.

## H5 — Generation-blind chef-stage mutations can target generation 2 instead of the generation the player acted on

- **Severity:** High
- **Section/line:** Addendum §1.6 lines 225–267; §2.3 lines 436–445 (current-generation scoping with unchanged signatures); §4.2 lines 769–774. Core Bank and recipe-retry calls carry no generation (`routes_livechat_cookout.py:405-437,541-570`); the new vote route at §4.2 line 757 is likewise generation-blind, while T4 routes correctly include one at lines 761–763.
- **Problem:** Concept ids are reused after a swap, but Bank, vote, and concept/picture/recipe retry do not name the generation the caller saw. “Use whatever generation is current when the write runs” is not a stale-request guard. Bank idempotency is also scoped to a per-generation recipe row, and generation-1 failed/unavailable rows (and their move ids) are deleted on swap, so a replay can become a brand-new generation-2 job.
- **Failure scenario:** Bank generation-1 concept `a` with move id `M`; its response is lost. Complete the swap and wait for generation 2 to become ready, then retransmit the identical request. The generation-2 `(a)` row is absent, so the server starts a new recipe instead of treating `M` as an already-recorded move. The player has unintentionally banked a different dish. The same missing fence lets a delayed retry or vote created against generation 1 mutate generation 2 once it is ready.
- **Exact fix:** Add an expected `generation` to every pre-existing chef-stage mutation (Bank, vote, concepts/pictures/recipe retry), validate it against the round inside the same write transaction, and return `409 bad_state` on mismatch; the updated client sends the view’s generation, while generation-1 core traffic is unchanged. For Bank, check a persistent `(anchor, conceptId, moveId)` replay record across **all** generations before starting a current-generation job, and retain that record even when failed/unavailable generation-1 recipe rows are dropped (a small round-level move ledger is sufficient). A replay must return `200` with no new job. Add tests for a lost generation-1 Bank response replayed after generation 2 is ready, stale retry/vote rejection, and a genuinely new generation-2 move succeeding.
