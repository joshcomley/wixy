## Remaining HIGH: Kimi H4 — linking is still not bound to the thumbnail selected

**Fold locations:** S §1.8, lines 325–337; §4.2, lines 845–850; §9, lines 1269–1270; Appendix A.2, lines 1524–1534. The behavior and client sections promise the displayed `attachmentId` is linked, but the request/store input does not carry that identity.

**Concrete sequence:** a mini-chat message has photo A at ordinal 0 still `processing`, and photo B at ordinal 1 already `ready`. GET correctly displays B as the lowest-ordinal ready photo. A finishes while that chooser is open. The player taps B, but POST sends only the message sequence; recomputing the specified selector now picks A. A valid photo silently replaces the one the player selected.

This is supported by the implemented queue, not an assumed future capability: `wixy_server/livechat/media_queue.py:312–342` runs two photo/voice tasks and dispatches each attachment independently; `wixy_server/livechat/store.py:4714–4750` commits each attachment's readiness separately. Messages may already reference processing attachments (`store.py:1664`).

**Measured check:** an in-memory database initialized by the real `LiveChatStore._migrate`, two real attachment rows, and the real `finish_attachment` method reproduced the folded selector changing between reads:

```json
{"schema_version": 21, "chooser_attachment": "photo-1", "link_attachment_after_earlier_photo_finishes": "photo-0", "mismatch_reproduced": true, "disk_database_created": false}
```

This checks the proposed selection rule against actual readiness transitions; it does not claim the unimplemented twist photo endpoint was executed.

**Exact remaining fix:** carry the already-returned `attachmentId` in the photo-link POST and `link_cookout_photo` signature. In the write transaction, validate that exact attachment is a ready photo on the supplied ordinary, non-view-once message in this round, and store that exact ID. Never silently substitute a freshly selected lowest ordinal. Define unlinking with null identifiers. Update §1.8, §4.2, the frozen interfaces and the client consistently. Add a GET-then-completion-then-POST test with processing-first/ready-second; the originally shown attachment must be linked, or an explicit stale-selection response must require reselection. Preserve the two existing static tests.

## NEW HIGH N1 — The new current-generation check disables T4 on archived banked recipes

**Introduced by the fold:** S §2.3, lines 512–516, newly puts **“the T4 writes”** in the group that uses the request generation **“after checking it is current”**. §1.10, lines 373–379, also mentions T4 immediately before the general generation-mismatch rejection, without an explicit exception.

**Contradiction and failure:** §1.8 says T4 applies to any banked recipe of any generation (315–331), §1.6 preserves T4 for banked earlier dishes (285–288), and the required e2e flow marks/rates/photographs generation 1 after swapping to generation 2 (1235–1237). Bank `a` in generation 1, complete a swap, then mark that saved recipe cooked: a literal implementation of the new §2.3 rule returns `409 bad_state` because `1 != 2`. The same rule blocks rating, photo linking/unlinking and unmarking every archived banked recipe. The core's current-dish Bank/retry checks (`store.py:4135–4141,4237–4245`) cannot serve as a blanket rule for the newly introduced archive-edit endpoints.

**Exact fix:** split the contracts in §1.10 and §2.3. Bank, vote and concepts/pictures/recipe retries must target the current generation (subject to the recorded Bank replay exception). T4 must instead resolve the explicitly named `(anchor, generation, concept_id)` banked recipe, verify the caller is a bound round player, and apply its cooked/rating/photo prerequisites **without requiring that generation to equal the round's current generation**. Keep the explicit generation in every T4 SQL predicate; never redirect it to current. State the exception alongside the frozen T4 signatures. Add store/route tests that mark, unmark, rate, link and unlink generation-1 recipes after a swap, including when generation 2 also has a banked `a`, and prove generation 2 is untouched. The existing end-to-end archived-recipe scenario must pass.
