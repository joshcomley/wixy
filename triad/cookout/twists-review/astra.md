## H1 — Requests do not identify which generation's dish the player selected

- **Severity:** High.
- **Section/line:** §1.7, lines 273–281; §2.3, lines 436–441; §4.2, line 757; Appendix A.2, lines 1378–1385. The inherited Bank/retry routes are defined in core §4.2, lines 760–765.
- **Problem:** Generation 2 reuses concept IDs `a`, `b`, and `c`, but voting accepts only `{sender, conceptId}`, and the existing Bank/recipe-retry requests and store signatures remain generation-free. Scoping a write to the database's *current* generation does not establish which dish the caller saw. `moveId` cannot establish that either: `bank_cookout_concept` currently uses the existence/state of `(anchor, concept_id)` for idempotency, rather than looking up a globally retained move receipt (`store.py:4142–4167`). The client also retries the same Bank request without a dish-generation identifier (`admin-ui/src/server/cookout/cookoutGame.ts:462–474`).
- **Failure scenario:** A phone displays generation-1 dish `a`. A vote or Bank request is delayed; the other phone completes a rescue swap, and generation-2 concepts become ready. The delayed request now votes for or banks the unrelated generation-2 dish `a`. A replay of an already successful generation-1 Bank can likewise start a second recipe job in generation 2 if its `a` has not yet been banked. No pending recipe existed when the swap committed, so the pending-recipe guard does not prevent this.
- **Exact fix:** Carry the displayed `generation` through vote, Bank and generation-specific retry requests, their TypeScript calls, and the corresponding store methods. Within the write transaction, reject an unrecorded request for a non-current generation with `409 bad_state`; recognize a recorded `(anchor, generation, moveId)` replay without starting another job. Preserve generation-1 compatibility for old requests only while the round is still generation 1; a missing generation must never select a generation-2 target. Update the frozen interfaces accordingly. Require tests that hold a generation-1 vote/Bank request until generation 2 is ready, and replay a completed generation-1 Bank after the swap: none may change generation-2 votes, recipes, events or job counts.

## H2 — Keeping the AI write interfaces unchanged permits an old job to claim a new generation

- **Severity:** High.
- **Section/line:** §1.6, lines 249–255; §2.3, lines 436–441; §5.3, lines 958–961; Appendix A.2, lines 1378–1385; §8, lines 1057–1072.
- **Problem:** A swap resets concept `run_id` to `NULL`; new recipe rows also start with `run_id = NULL`. Existing concept/recipe claim and completion interfaces have no captured dish generation. Adding `generation = (SELECT generation FROM cookout_rounds ...)` to recipe statements selects the new row rather than fencing a stale worker out. The assertion that no pending old recipe remains is insufficient: a second worker can still be inside an outstanding spawn after another worker has completed that recipe. The image fence addresses only pictures.
- **Failure scenario:** Two v22 processes read a generation-1 `pending/NULL` job. Worker A's cmd spawn is slow. Worker B records its own run and completes generation 1; a rescue swap then creates generation 2 in `pending/NULL`. A's spawn returns, and `set_cookout_concepts_run(..., expected_run_id=None)` accepts A's generation-1 run into generation 2. A validates against its captured old basket and can store those old concepts as the new dishes. The equivalent recipe race occurs if generation-2 dish `a` is banked before A returns. `cookout_ai.py:1015–1075`, `1125–1176`, and `1182–1209` capture the old prompt/validation context but guard only state and run ID; `store.py:3842–3900` and `4171–4227` perform the unfenced writes. In an in-memory database migrated with the addendum's SQL, the actual unchanged concept setter accepted this late claim: `True`, with `{generation: 2, concepts_run_id: 'late-gen1'}`.
- **Exact fix:** Add an explicit captured `expected_generation` to concept and recipe claim/completion methods and their runner protocols. Check it in SQL alongside state and run ID; recipe writes must target the captured generation, not a subquery for whichever generation is current. Carry the same captured identity through polling, repair, unavailable/failure and exception paths, and key local running-job suppression by generation. A losing spawn must be cancelled. Update the frozen X2↔X3 contract instead of promising unchanged signatures. Require two-worker tests that delay generation-1 spawn success *and failure* across completion, swap and generation-2 startup; no old callback may claim, finish or fail the new job. Retain the separate existing image-attempt fence.

## H3 — The documented v21 overlap limit misses writes that bypass the new game rules

- **Severity:** High.
- **Section/line:** §2.3, lines 442–445; §7, lines 1032–1033; §8, lines 1047–1049.
- **Problem:** The rollout contract permits an old v21 process to keep serving the migrated database and describes only a possible generation-1 recipe misfile. The actual v21 process accepts a newer schema (`store.py:1293–1297`) and continues executing all of its old mutations and background recovery. Its Turn-10 pick unconditionally starts concepts (`store.py:3796–3812`), and its AI read still derives the basket from the ten original turn choices (`store.py:3604–3608`). Thus it can bypass the new gates and ignore wildcard/swap baskets; this is not confined to inserting a recipe under the wrong key. Background recovery is also independent of which slot receives new HTTP traffic (`cookout_ai.py:860–880`).
- **Failure scenario:** During the permitted overlap, a v21 process handles the final pick of a round with stars and cloche enabled. The chef starts before either star or the cloche is answered; the new star endpoint then regards the stars as locked because concepts have left `none`. An in-memory check applied the addendum's real migration SQL and played ten legal turns through the actual v21 `pick_cookout`: the final row was `{state: 'finished', concepts: 'pending', stars: 1, star1_id: null, star2_id: null, wildcard: 'armed'}`. An old recovery worker can similarly start a pending new-generation job using its old ten-choice basket. The accepted "seconds of overlap" description does not make these durable writes safe.
- **Exact fix:** Specify a rollout boundary that stops/drains all v21 Cookout writers and recovery workers before any v22 twist state can be created or advanced. If uninterrupted blue/green operation is required, first deploy a compatibility release that fences those old mutations and workers when a newer Cookout schema/feature epoch is active; enable twists only after that fence is everywhere. Routing new requests alone is insufficient. Document the corresponding rollback restriction. Extend migration/rollout tests to run an old writer and old recovery worker against a v22 fixture and prove that they cannot advance a gated round or claim a changed basket. Replace the stated misfile-only limit with this enforced deployment contract.

## H4 — Stars reveal while the cloche gate still allows them to change

- **Severity:** High.
- **Section/line:** §1.4, lines 183–195; §1.5, lines 205–214; §1.9, line 324; §8, lines 1052–1059.
- **Problem:** The addendum defines star changes as legal on any finished round whose concepts are still `none`, and locks them only when concepts leave `none`. It separately reveals both stars as soon as the round is finished and both star IDs exist, calling that "the moment the stars lock." With an unanswered cloche, those are different moments. A literal implementation exposes the supposedly committed secret choices while allowing both players to revise them after inspecting the other's choice.
- **Failure scenario:** Both players star an ingredient during drafting, with wildcard enabled. Turn 10 finishes the round, reveals both stars, and leaves concepts at `none` because wildcard is `offered`. Either player can now change their star after seeing the partner's. Alternatively, when the second star is submitted at the gate before answering the cloche, that submission reveals both without locking either. The existing test list covers gate ordering but does not assert this lock/reveal boundary.
- **Exact fix:** Make star revelation and commitment the same transition, independent of the cloche. Keep the stated reveal predicate (`finished` and both stars set), and forbid changing either star whenever that predicate is true, even while concepts remain `none`; an identical-value replay remains a no-op. Also retain the prohibition once concepts have started. Reflect this rule in the view and disabled controls. Require Open and Blind tests for both stars chosen before Turn 10 and the second star chosen after Turn 10, with the cloche still unanswered: stars reveal together, every different subsequent star is rejected, and clearing the cloche starts exactly one job with those locked IDs.

## H5 — A swapped-out pickable staple remains allowed in the regenerated dishes

- **Severity:** High.
- **Section/line:** §1.6, lines 228–237; §5.3, lines 914–917 and 928–957; `ConceptTwists`/`RecipeTwists`, lines 963–976; §8, lines 1067–1071.
- **Problem:** Rescue swap allows every non-starred basket ingredient, including the five pickable cupboard staples. §5.3 then promises that Pass 1 rejects *any* mention of the swapped-out ingredient, but the prompt still supplies the core staple list and neither twist context carries a forbidden swapped-out ID. Core §2.2 explicitly permits unpicked butter/flour/oil/sugar/milk as declared staples. The implemented scanner likewise allows a declared staple (`cookout_bank.py:399–432`), and `basket_payload` always emits all eight staples (`cookout_ai.py:191–194`). Treating a swapped-out item as merely "unpicked" cannot deliver the stated exclusion.
- **Failure scenario:** Butter was drafted, then rescue-swapped for a new ingredient. The generation-2 chef declares `butter` in `stapleIds` and uses it throughout the dishes and full recipes. Both the core structural rules and lexical passes accept it, so the ingredient the players removed returns immediately. A direct check against the implemented bank returns no violations for `"brown the butter"` with no picked ingredients and `allowed_staple_ids={'butter'}`.
- **Exact fix:** Add the completed swap's forbidden food ID to the X2↔X3 read/context contract for the current generation. Exclude that ID from available staples in the prompt, reject it in every returned ingredient/staple manifest, and apply an explicit forbidden-ID lexical check that cannot be overridden by declared-staple, family or omission allowances. Keep this exclusion scoped to generation 2 so archived recipes remain intact. This adds only a validated bank ID to prompts, preserving privacy. Require swap tests for each of `butter`, `plain-flour`, `cooking-oil`, `granulated-sugar`, and `milk`, including explicit staple declarations, aliases and omission reasons; the regenerated dishes must reject each removed item while generation-1 recipes remain readable.
