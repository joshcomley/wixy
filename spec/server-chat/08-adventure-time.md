# Server chat — Adventure Time (the globe holiday game)

Workspace 00056. Decided brief: implement faithfully. Where reality contradicts a cited fact, prefer
reality and record it in the decision entry (`decisions/00190-server-chat-adventure-time/`).

## 0. The ask (operator, verbatim summary)

A second game in the chat's ⋯ menu, **"Adventure Time"**. It brings up a globe. One of you spins
it sideways; the other sees the finger swipe as a pen-like trail that thins at its end and fades
quickly; the globe spins, spins, spins and lands. Then the up/down spin, which lands too. If the
landing is in the sea it goes to the nearest land. Because the sea funnels landings onto coasts,
the game then spins round and zooms in to a point **30 % inland** from that coast, and nearby
countries **light up at random, about four a second**; you press **Stop** at the bottom and it
zooms into the country that was lit. Then it takes that country's **top five holiday
destinations** and does the same again; Stop zooms into the destination and lets you explore. An
AI then says **"Preparing holiday pack"**, researches the place live on the internet (a couple of
minutes) and comes back with the food, a couple of nice villas or places to stay, the culture
(theatre, things to see), the sights and what to do. **"Bank this"** (the operator's wording, 2026-10-28; originally "Let's go there") banks it (saved);
**"No"** rejects it and it **never appears again** in the destination draws. Every destination has
its own **mini chat** at the bottom (expandable), exactly like the would-you-rather game, and it
must SHARE that code: improving the per-item mini chat improves every game.

Operator decision #2113 (answered 2026-10-28): the second spin is up/down; either person may do
any step (the UI shows whose turn it is but never blocks); cmd's retained copy of each research
job is fine; places under a UK "advise against all travel" for the whole country are left out —
**and that must be toggleable** (§2.2, §4.1 `adv_settings`, §5.3 Options).

## 1. Flow and states

`adv_rounds.state`:

```
spin_lng  --spin(axis=lng)-->  spin_lat  --spin(axis=lat, result)-->  country
country   --stop(country)-->   destination   (or straight to chosen when only one is left)
destination --stop(destination)--> chosen   (pack job starts)
chosen    --decide(bank)--> banked   |   --decide(reject)--> rejected
spin_lng|spin_lat|country|destination --(a new adventure starts)--> abandoned
```

`adv_rounds.pack`: `none` (before chosen) → `pending` → `ready` | `failed` | `unavailable`
(`unavailable` = no researcher configured, e.g. the standalone edition, or cmd unreachable at
start). `failed` → retry → `pending`. Bank/Reject are allowed in `chosen` whatever the pack state;
a pack still `pending` when the round is banked still lands on the row.

Starting an adventure abandons every round in `spin_lng|spin_lat|country|destination`. A `chosen`
round is never abandoned (it is a real destination waiting for a decision).

**Who:** anyone unlocked may do any step. Each step records the display name (`by`) so the UI can
say "Bubble spun it" and prompt "Cupcake's turn" (the other name), but nothing is refused for
being the "wrong" person. Concurrent attempts serialize in the store: the first wins; the loser
gets `409 bad_state` and its client re-reads the view and animates the winner's move.

## 2. Data (static repo content)

### 2.1 The world map — `admin-ui/data/adventure-world.json`

Generated by `tooling/adventure/build_world.mjs` (Node; its OWN `tooling/adventure/package.json`
with devDeps `topojson-server`, `topojson-simplify`, `topojson-client`, `polylabel`, so the admin
bundle's dependencies are untouched) from **Natural Earth 1:50m** (public domain), downloaded from
`nvkelso/natural-earth-vector` at a PINNED commit SHA named in the script header.

- **Units**: `ne_50m_admin_0_countries`, except that **FRA, PRT, NOR, NLD, TZA, GBR** are replaced
  by their `ne_50m_admin_0_map_units` pieces (France/Martinique/Guadeloupe/French Guiana/Réunion/
  Mayotte; Portugal/Madeira/Azores; Norway/Svalbard/Jan Mayen; Netherlands/Caribbean Netherlands;
  Tanzania/Zanzibar; England/Scotland/Wales/Northern Ireland). Id = `ADM0_A3`, or `GU_A3` for a
  split piece (`FXX`, `MTQ`, `GLP`, `GUF`, `REU`, `MYT`, `PRX`, `PMD`, `PAZ`, `NOR`, `NSV`, `NJM`,
  `NLD`, `NLY`, `TZA`, `TZZ`, `ENG`, `SCT`, `WLS`, `NIR`). 256 units. Ids are permanent.
- **One TopoJSON, two objects** sharing ids: `detail` (lightly simplified, for zoomed views and
  ALL geometry decisions) and `coarse` (heavily simplified, for drawing the spinning globe).
  Quantized; target ≤ 600 KB total uncompressed. Feature properties: `{ name }` only (the bank
  carries display names); `id` on the geometry.
- **Part centres**: for every polygon part of every `detail` feature above a tiny area, its pole
  of inaccessibility (`polylabel` on an equirectangular projection of that ring set, precision
  ~0.05°), stored as a top-level `centres: { [id]: [[lng,lat], …] }` in part order. Used for the
  30 %-inland step (§3.3).
- **Served** as a static asset: `esbuild.config.mjs` copies it to
  `wixy_server/static/admin/adventure-world.json` and defines `WIXY_ADVENTURE_WORLD_URL` with a
  content hash (`?v=<sha256[:10]>`), the call-worklet precedent. The client fetches it lazily
  the first time the game or a card needs it. Behind CF Access like every admin static file;
  it contains no chat data.
- A drift test re-runs nothing over the network; the script's output is committed and the CI
  bundle-drift check covers the static copy.

### 2.2 The destination bank — `wixy_server/livechat/adventure_destinations.json`

```json
{ "version": 1, "generated": "2026-10-28",
  "countries": {
    "PRX": { "name": "Portugal", "advice": null,
             "destinations": [
               { "id": "PRX.lisbon", "name": "Lisbon", "region": "Lisbon",
```

  `blurb` ≤ 120 chars, plain text.
- A unit with no realistic holiday destination (uninhabited: Antarctica, Heard Island, Bouvet,

- Written by AI writers per region, then machine-checked by `tooling/adventure/validate_bank.py`:
  schema, id/slug rules, uniqueness, rank count, and that every destination point lies inside its
  unit's `detail` geometry or within 25 km of it (islands, coastal resorts). The validator runs in
  pytest (`test_adventure_bank.py`) so the committed bank can never drift from the map.

## 3. Geometry and motion (client; one implementation, in TypeScript)

The client that makes a move computes its consequence and posts it; the server validates the
shape and bounds and stores it; every other client replays it from the stored values. There is no
second (Python) geometry implementation. This is a game between two trusted people (Inv 40's
trust model): the server enforces consistency (one outcome, stored once, replayed everywhere),
not anti-cheating.

Runtime deps added to `admin-ui`: **`d3-geo`** (orthographic projection, canvas paths, clipping,
`geoContains`, `geoDistance`, `geoInterpolate`) and **`topojson-client`**. Both are bundled by
esbuild (self-hosted; no CDN, no framework).

### 3.1 The globe and the two spins

- Orthographic projection, `rotate([λ, φ])`. A fixed **pin** marks the centre of the globe; the
  landing point is whatever geography is under it: `projection.invert(centre)`.
- Spin 1 (`axis: "lng"`) changes only λ (horizontal drag); spin 2 (`axis: "lat"`) changes only φ
  (vertical drag; the globe tumbles over the poles freely — φ is unbounded).
- Drag: the globe follows the finger (Δangle = Δpixels / radius in degrees, axis-locked).
  Release velocity = the angular speed over the last ~80 ms of samples. **A flick is
  |ω| ≥ 120°/s**; anything slower just leaves the globe where it was dragged ("Flick it
  harder!").
- **Spin outcome** (`physics.ts`, pure): `Δ = sign(ω) · clamp(|ω| · 1.5, 720, 3600)` degrees,
  `D = clamp(3 · |Δ| / |ω| · 1000, 3500, 7000)` ms, angle(t) = from + Δ · easeOutCubic(t / D).
  The server validates `720 ≤ |delta| ≤ 3600`, `3500 ≤ durationMs ≤ 7000`, `from` finite and
  |from| ≤ 1e6.
- Before the first spin the globe idles slowly (local only) at φ = −15.

### 3.2 Landing

`land.ts` (pure, d3-geo, `detail` features, eligible set from the view):

1. `P = invert(centre)` at the final rotation (spin 2's end).
2. If `P` is inside an **eligible** unit → `L = P`, `unit = that`, `sea = false`.
   Else (sea, or a non-eligible unit such as Antarctica) → `L` = the nearest point on any eligible
   unit's boundary (great-circle distance, bbox-prefiltered), `unit` = its owner, `sea = true`.
3. **Inland centre**: if `sea`, `C = geoInterpolate(L, partCentre)(0.30)`, where `partCentre` is
   the §2.1 centre of the polygon part of `unit` that contains `L` (or is nearest to it).
   If not `sea`, `C = P`.
4. **Candidates**: eligible units by distance from `C` (0 when `C` is inside), keep those ≤ 500 km;
   if fewer than 4, add the nearest until there are 4 or the next is > 2500 km; cap at 10. The
   containing/landing unit is always first. Order the final list by distance.

Spin 2's POST carries `{point: P, sea, land: L, centre: C, landUnit, candidates}`. Server checks:
coordinates in range, `landUnit` and every candidate are bank units, 1–10 unique candidates,
`landUnit` ∈ candidates.

### 3.3 Camera

- After spin 2 stops: a ripple at the pin. If `sea`, a dotted glide from `P` to `L` with the
  label "Nearest land: <unit>" (≈1.5 s). Then "spins the globe around and zooms in": animate
  rotation to centre `C` and scale so the candidates fit (fit radius = the largest angular
  distance from `C` to each candidate's nearest point, ×1.25, min 3°, max 40°; scale so that
  `R·sin(fit) = 0.45 · min(width, height)`), ≈2.5 s, ease-in-out. Switch from `coarse` to
  `detail` drawing once the angular view radius < 60°.
- Destination stage: centre on the mean of the destination points (spherical), fit them plus a
  margin (min 1.5°).
- Chosen: zoom to the destination (view radius ≈ 1.2°), the pin drops on it. The map then becomes
  **explorable**: drag rotates, pinch/wheel zooms (view radius 0.3°–90°), a "Back to the place"
  button recentres. Every animation can be watched mid-flight by a late joiner: all timing is
  derived from server timestamps (§4.4) so a client that opens the tab late jumps to the right
  point.

### 3.4 Roulettes (country, then destination)

- Server stores `rouletteAt` (epoch seconds when flicker starts) and `seed` (uint32) per stage.
  Step `k = floor((serverNow − rouletteAt) / 0.25)` (four a second). Lit index sequence
  `roulette.ts`: `i0 = r0 · n`, `i_k = (i_{k−1} + 1 + floor(r_k · (n − 1))) mod n` (never the same
  twice running) with `r_k = mulberry32(seed + k)`. Both screens show the same lit item (within
  clock-sync error).
- `country.rouletteAt = now + spinRemaining + 5.0` (glide + zoom); `destination.rouletteAt =
  now + 3.5` (settle + zoom). The Stop button appears at `rouletteAt`; the server refuses an
  earlier stop (`409 too_early`, 1 s tolerance).
- The lit country fills bright (others muted) with its name in a large label; the lit destination
  dot glows with its name + blurb. Haptics (`navigator.vibrate(8)`) on each step where supported
  and not reduced-motion.
- **Stop** posts the id the presser SAW lit (`{stage, choice}`) — what you see is what you get.
  Both screens then settle on that choice (a short pulse), then the next camera move.
- `prefers-reduced-motion`: no flicker animation beyond the label change, no camera tweening
  (cuts instead), trail not drawn.

### 3.5 The live swipe trail

- While a spin drag is in progress the dragger's client sends live frames (paced like live
  drawing: ≤ 20 frames/s, one in flight, keepalive) to `POST /adventure/live`:
  `{anchorSeq, clientId, axis, rotation: [λ, φ], points: [[x, y, t], …], frame, end}` — points are
  the finger positions since the last frame in **globe-radius units relative to the globe centre**
  (so any screen size maps), `t` ms since the drag began; ≤ 32 points; |x|,|y| ≤ 3.
- Every other screen showing that round (and in the matching spin state, not mid-animation)
  applies `rotation` and draws the trail. The dragger draws its own trail locally.
- **Trail look** (`trail.ts`): a pen-like stroke along the recent points; width tapers from 9 px
  (newest) to 0 at the tail; each point fades out over 450 ms; drawn with round caps, white with a
  soft shadow over the globe. Never persisted; dropped on lock (Inv 53's live-drawing rules apply).
- The committed spin (the POST at release) is what decides the outcome; the live frames are
  cosmetic and lossy. A watcher animates the committed spin from its stored `from` (which equals
  the last live rotation), so the hand-off is seamless.

## 4. Server

### 4.1 Schema v20 (`store.py`, additive; v19 is deployed and never edited)

```sql
CREATE TABLE IF NOT EXISTS adv_rounds(
  anchor_message_seq INTEGER PRIMARY KEY REFERENCES messages(seq) ON DELETE CASCADE,
  state TEXT NOT NULL CHECK(state IN ('spin_lng','spin_lat','country','destination','chosen',
                                      'banked','rejected','abandoned')),
  started_by TEXT NOT NULL,
  spin_lng TEXT, spin_lat TEXT,        -- JSON {by, from, delta, durationMs, at}
  landing TEXT,                        -- JSON {point, sea, land, centre, landUnit}
  country_candidates TEXT, country_seed INTEGER, country_roulette_at REAL,
  country_id TEXT, country_by TEXT,
  dest_candidates TEXT, dest_seed INTEGER, dest_roulette_at REAL,
  destination_id TEXT, destination_by TEXT,
  pack TEXT NOT NULL DEFAULT 'none' CHECK(pack IN ('none','pending','ready','failed','unavailable')),
  pack_run_id TEXT, pack_json TEXT, pack_error TEXT,
  decided_by TEXT,
  rev INTEGER NOT NULL DEFAULT 1,
  created_at REAL NOT NULL, updated_at REAL NOT NULL);
CREATE INDEX IF NOT EXISTS idx_adv_rounds_state ON adv_rounds(state);
CREATE TABLE IF NOT EXISTS adv_rejected(destination_id TEXT PRIMARY KEY);
CREATE TABLE IF NOT EXISTS adv_settings(
  id INTEGER PRIMARY KEY CHECK(id = 1),
  include_advised INTEGER NOT NULL DEFAULT 0 CHECK(include_advised IN (0, 1)));
```

- `adv_settings` is the game's shared preference (one row; no row = defaults): today only
  `include_advised` (operator decision #2113 — places under a whole-country "advise against all
  travel" are left out unless this is on). It is a preference naming no place and no person, so —
  like `wyr_topics` — a wipe leaves it alone.

- `adv_rounds` follows `wyr_rounds` exactly (Inv 54 pattern): keyed by the anchor message, cascade
  on delete (an older blue/green process still erases it), explicit `DELETE` in wipe.
- `adv_rejected` is the **never-again list**: destination ids only, no dates, no FK. It survives
  deleting the round's message (that is what "never appears again" means) and a **wipe clears it**
  (a wipe forgets everything about the two of you). Banked destinations are derived from
  `adv_rounds.state = 'banked'` (no second table; deleting the trip's message removes it from the
  bank).
- **Game chat reuses `wyr_chat`** (it is already a generic `message_seq → anchor_seq` table, both
  FKs to `messages`). `create_message(..., wyr_anchor_seq=)` now accepts an anchor that is a
  would-you-rather round OR an adventure round (404 otherwise). The wire keeps its historical
  names `wyrSeq`/`wyrRef`: they mean "the game-chat anchor of ANY game" (renaming would break
  cached clients mid-deploy; documented in contracts.md and the glossary).

### 4.2 Wire

- `Message.adventure = {state, pack, rev} | null` (joined at read time like `wyr`).
- `POST /api/admin/server/adventure` `{clientId, deviceId, sender}` → `201 {message}` (`200` on a
  replayed clientId). Abandons open rounds (§1). The anchor is a text-less message (like WYR's).
- `GET /adventure/{seq}` → the view:
  ```
  { seq, state, rev, serverNow, startedBy,
    eligible: [unitId] | null,           // only while state is spin_lng|spin_lat
    spins: { lng: Spin|null, lat: Spin|null },   // Spin = {by, from, delta, durationMs, at}
    landing: {point, sea, land, centre, landUnit, landUnitName} | null,
    country: { candidates:[{id,name}], seed, rouletteAt, chosen:{id,name}|null, by } | null,
    destination: { candidates:[Dest], seed, rouletteAt, chosen: Dest|null, by } | null,
    pack: { state, data: Pack|null, error: string|null },
    decidedBy: string|null }
  ```
  `Dest = {id, name, region, lat, lng, kind, blurb}`. `eligible` = bank units with ≥ 1 remaining
  destination (remaining = bank − rejected − banked).
- `POST /adventure/{seq}/spin` `{sender, axis, from, delta, durationMs, result?}` (`result` required
  for `lat`, refused for `lng`). Stores `at = now`. On `lat`: stores landing + country candidates,
  `country_seed = random uint32`, `country_roulette_at = now + durationMs/1000 + 5.0`.
- `POST /adventure/{seq}/stop` `{sender, stage: "country"|"destination", choice}` — `choice` ∈ that
  stage's candidates. Country stop: picks the top ≤ 5 remaining destinations of the unit in rank
  order, taking one only if it is ≥ 40 km from every one already taken (so roulette dots never sit
  on top of each other), then filling any shortfall from the skipped ones in rank order; skipped
  ones stay in reserve; 0 remaining → `409 exhausted`; exactly 1 → state `chosen` directly (destination stage
  skipped); else state `destination`, `dest_seed`, `dest_roulette_at = now + 3.5`.
  Destination stop → `chosen` and the pack job starts (§4.3).
- `POST /adventure/{seq}/decide` `{sender, decision: "bank"|"reject"}` — only from `chosen`.
  Reject also inserts the destination into `adv_rejected` (same transaction).
- `POST /adventure/{seq}/pack/retry` `{sender}` — only when `pack` is `failed` (or `unavailable`
  and a researcher now exists).
- `GET /adventure/bank` → `{trips: [{seq, unitId, unitName, destination: Dest, headline|null,
  pack}]}` newest first (declared BEFORE `/adventure/{seq}`).
- `GET /adventure/settings` → `{includeAdvised: bool, advisedUnits: [{id, name}]}`;
  `PUT /adventure/settings` `{includeAdvised: bool}` → the same (declared BEFORE `/adventure/{seq}`).
  A change takes effect for rounds still in `spin_lng`/`spin_lat` (their view's `eligible` is
  computed at read time) and publishes so both screens re-read.
- `POST /adventure/live` — §3.5; validated like `/drawings/live` (ids 8–64 chars, anchor a real
  seq, frame counter bounded, ≤ 32 points, bounded coordinates, axis enum, finite rotation);
  rate-limited 30/s on the same authenticated identity key as drawing live (its own limiter);
  relayed to every open stream as SSE event **`adventure_live`** by the live broker (generalise
  `DrawingBroker` to carry the event name; drawing behaviour unchanged). Never stored or logged.
- Errors: `404 not_found`, `409 bad_state` (wrong state / a different move already made),
  `409 too_early`, `409 exhausted`, `422 invalid`. Every mutation is idempotent: replaying the
  SAME move (same axis+from+delta, same stage+choice, same decision) returns `200` with the view;
  a DIFFERENT move after the state advanced is `409 bad_state`. All mutations publish via the
  existing notifier → `message_updated` (no new persisted event type).

### 4.3 The holiday pack job (`adventure_pack.py`, cmd via `cmdchat.py` — Inv 13)

- `cmdchat.py` gains the chat-spawn run calls (`POST /api/chat-spawn/runs`, `GET …/{run_id}`,
  `POST …/{run_id}/cancel`) — the ONE chokepoint to cmd. Body: `caller: "wixy-adventure-pack"`,
  `model: "claude-sonnet-5-5"`, `effort: "medium"`, `spawned_by_session_id: ""`,
  `cwd: <storage>/projects/<slug>/server/adventure-research` (an empty non-git folder this server
  creates), `bucket: "subscription"`, `timeout_secs: 1200`, `tag` omitted (hidden system chat),
  `disallowed_tools: ["Bash","PowerShell","Edit","Write","MultiEdit","NotebookEdit","Read","Grep",
  "Glob","Agent","Task","Skill","TodoWrite"]`. Response: `run.run_id`; poll `run.status`
  (`queued|running|completed|error|timeout|cancelled`) and read `run.response_text` (the final
  assistant message only).
- **The prompt names only the destination** (name, region, unit name, coordinates) — never a
  person, a message or anything from the chat. It asks for live web research (WebSearch/WebFetch
  only) and a FINAL message that is exactly one JSON object:
  ```
  { "headline": str≤140, "summary": str≤700,
    "sections": [ { "key": "food"|"stay"|"culture"|"sights"|"do"|"practical",
                    "title": str≤60,
                    "items": [ { "name": str≤90, "detail": str≤400, "url": str|null } ] ≤ 6 } ] ≤ 6,
    "bestTime": str≤240, "gettingThere": str≤300, "travelAdvice": str≤400,
    "sources": [ { "title": str≤120, "url": str } ] ≤ 12 }
  ```
  `stay` asks for 2–4 specific villas or characterful places with links; `food` for the dishes the
  area is known for plus 2–4 specific places; `culture` theatre/music/festivals/museums/customs;
  `sights`; `do`; `practical` costs/currency/language. `travelAdvice` = the current FCDO headline,
  fetched from the country's gov.uk page itself. Voice: a warm, knowledgeable friend talking to
  the couple ("you"); never mention itself, its searches or its sources in the text; leave out
  what it could not confirm. Measured 2026-10-28 (Kotor trial run): completed in 61 s, one JSON
  object within every limit.
- Parsing is defensive: take the last JSON object in `response_text`; validate and clip every
  string; keep only `http(s)` URLs with a host (≤ 500 chars); drop unknown keys; a pack with no
  sections is a failure. Stored as canonical JSON in `pack_json`.

### 4.3a Pictures in the pack (operator request 2026-10-28: "make the holiday pack … include pictures")

- The JSON gains `hero: [{url, caption ≤120, credit ≤120, page}] ≤ 6` (photos of the place) and,
  per item, `image: {url, credit ≤120, page} | null`. The prompt asks for real PHOTOGRAPHS (no
  logos/maps/icons), DIRECT image-file URLs it actually saw (Wikimedia Commons `upload.wikimedia.org`
  files, the venue's or tourist board's own images), with credit and source page.
- **Fetched by this server, never by the browser.** A viewer's device must not contact third-party
  image hosts from a private chat (it would reveal the viewer's address to them), so after the
  text pack is stored (`pack = ready`, the pack shows at once) a second step fetches the pictures
  server-side and stores them as the round's private media; the client shows placeholders until
  each arrives. Wire: `pack.images: 'pending' | 'done'` and each picture slot carries a signed
  media URL set (`thumb`, `full`) once stored, or nothing.
- **Fetch safety (security-sensitive; audited before merge):** `http(s)` only, port 80/443 only;
  resolve the host and refuse any loopback / private / link-local / multicast / reserved address
  (IPv4 and IPv6, including IPv4-mapped), connecting to the vetted address itself (no second DNS
  lookup — rebinding); every redirect re-vetted, at most 3; 15 s per fetch, ≤ 8 MB body
  (streamed, aborted beyond); `Content-Type` image/* AND the bytes sniffed as JPEG/PNG/WebP;
  decoded with Pillow under the existing decompression-bomb limit; refused if the short side is
  < 480 px or the aspect ratio is beyond 3:1 (icons, banners); re-encoded to JPEG (metadata
  stripped, Inv 16/44) at ≤ 1600 px plus a 480 px thumb; at most 16 pictures per pack, 4 fetches
  in parallel; no cookies, a plain descriptive User-Agent.
- **Fallback for the hero**: if fewer than 3 hero photos survive, query Wikimedia Commons'
  public API (`commons.wikimedia.org/w/api.php`, file-namespace search for "<destination>
  <unit>", `prop=imageinfo` with a 1600 px thumb URL, photographs only — `mime` image/jpeg) and
  take the best until 3–6. Credit = the file's artist + licence from `extmetadata`.
- **Storage and erasure**: pictures are the round's chat content — stored like the WYR round
  pictures (ordinary private photo attachments on the anchor message, signed URLs, quota,
  erased with the anchor or a wipe — Inv 46/56), excluded from the Gallery like WYR's, and
  never fetched again after storing. `pack_json` maps each slot (hero i / section key + item i)
  to its attachment ordinal.
- **Credits** show small under each picture ("Photo: <credit>"), linking to `page`.
- Job: on entering `chosen` → `pack = pending` → start the run, store `pack_run_id` → poll every
  10 s (bounded) until terminal or 25 min → store `ready`/`failed` (error text short and generic:
  "The research didn't finish — try again") → bump `rev`, publish. Spawn is single-file: at most 2
  research runs in flight (`CapacityLimiter(2)`), started ≥ 5 s apart (cmd's parallel-spawn
  gotcha). A cmd `error` within the first 150 s is retried once.
- **Restarts**: at startup every `pending` round with a `pack_run_id` resumes polling that run; one
  without (crashed before the spawn) starts a new run. Writes are compare-and-set on
  `(pack = 'pending' AND pack_run_id = ?)`, so a blue/green overlap where both processes poll
  stores once.
- **Edition**: fleet only (`create_app(adventure_researcher=…)` seam; default = a cmd-backed
  researcher when the AI backend is `cmd`). Standalone/none → `pack = unavailable` at once; the
  UI says holiday packs aren't available on this server and Bank/Reject still work.
- **Privacy (Inv 56)**: the pack is chat content — on the round row, erased with the anchor or a
  wipe. cmd keeps its own copy of each research run (prompt + final answer, in its hidden
  `chat-spawn` ledger and transcript) which this server cannot erase: the prompt is a function of
  the bank destination ONLY (the picture-pool argument of decisions/00183 — bank-derived, names no
  one), but its timestamp does say "a pack was researched then". Documented as an honest limit;
  operator decision #2113 Q3.

### 4.4 Time

Every view carries `serverNow`. The client keeps `offset = serverNow − localNow` from the
response with the smallest round-trip, and drives every animation and roulette from server time,
so two screens agree and a late joiner lands mid-flight.
