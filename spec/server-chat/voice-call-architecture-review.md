# Private two-person voice calls: architecture review

Review date: 2026-10-18. Scope: architecture only, workspace 48. No implementation or live audio test was performed. The supplied oracle result is rejected: device-grant and robots-header briefs do not establish a voice transport precedent. This ruling comes from the current source and the operator's binding requirements.

## Ruling

Choose **bounded mono PCM over a same-origin secure WebSocket through the existing Cloudflare HTTP tunnel**, for this small, private, two-person feature. Use AudioWorklet capture and playback, 24 kHz signed 16-bit little-endian PCM, 20 ms frames. Keep signaling and media outside the persistent chat event stream and database. No recording, transcription, attachments, call history, push notifications, or automatic answering.

This is a conditional engineering choice, not a claim that TCP is a better voice transport. WebRTC with Opus, jitter adaptation and TURN/UDP is the stronger general-purpose calling stack. WSS incurs TCP head-of-line blocking and requires us to implement bounded buffering, resampling, playout, drift handling and lifecycle safety. PCM costs 384 kbit/s per direction before framing; hub receives approximately 768 kbit/s and sends 768 kbit/s for a full-duplex pair. That is reasonable for one call, but must be measured on the actual connection.

Relay-only WebRTC would need a publicly reachable hub TURN service, credentials, certificates, firewall/NAT setup and monitoring. The current HTTP tunnel is not evidence of a reachable raw TURN endpoint. Do not open router ports, purchase a relay, or ship an inert TURN configuration switch as delivery. Do not substitute STUN-only peer-to-peer calls: they fail the hub-relay constraint and reliable external-network connectivity. If the real-audio gate below fails, return with evidence and seek the operator's decision on TURN exposure or another relay; do not hide the failure with larger latency buffers.

Cloudflare documents WebSocket support, but also connection termination during infrastructure restarts. Therefore an interrupted call ends; reconnecting presence must never resume audio automatically. This review has not verified the deployed hostname's WebSocket/Access configuration. See [Cloudflare WebSockets](https://developers.cloudflare.com/network/websockets/).

Transport confidentiality is TLS on the browser/edge/tunnel path, with CF Access and application authorization. PCM is available to the trusted relay process and Cloudflare termination; this is **not end-to-end encryption**. No audio is persisted by Wixy. If E2EE becomes a requirement, revisit this ruling rather than claiming WSS supplies it.

## What the current code actually establishes

* `wixy_server/auth.py::build_admin_auth_middleware` verifies `CF-Access-Jwt-Assertion` via `verify_access_jwt`, using RS256, the configured audience, team issuer and cached JWKS. It runs verification off the event loop. Its HTTP identity is the verified `email`, falling back to `sub`. It trusts the email header only in the explicit development bypass.
* `app.py` installs that gate with `app.middleware("http")`. It does **not** authorize WebSocket scopes. Its `jwks` instance is currently a local variable, not a documented `app.state` field available to a new WS route.
* `livechat/tokens.py::require_server_token` reads only `X-Wixy-Server-Token`, verifies its HMAC, absolute expiry and exact identity binding, and checks `is_device_grant_live(..., max_idle_s=GRANT_IDLE_EXPIRY_S)` for grant-bound tokens. Calling only `verify_unlock_token` would omit revocation protection.
* `routes_livechat.py::_stream_events` repeats expiry/grant checks during an SSE connection, with roughly a two-second revocation bound. Existing audio transcription is a separate opt-in subsystem: a call must not enter it.
* `admin-ui/src/server/chatView.ts` owns attach/detach/dispose and an attachment epoch. `attach` can run again while attached during token renewal or grant adoption. Thread and SSE lifecycle are separate from the proposed call lifecycle.
* `types.ts::SuspendReason` currently contains recording, micPermission, filePicker, mediaPlaying and viewOnce. `panel.ts` reference-counts reasons; the last release calls `armIdleTimer`, resetting both monotonic and wall-clock activity. `idleRanOutWhileAway` respects suspensions.
* `panel.ts` treats only filePicker/micPermission as hidden-tab exceptions. `lockModel.ts`'s shield transition issues `detachChat`; a harmless shield restoration reattaches later. This is material: shield must end a call too, even if the chat subsequently returns without a PIN.
* `recorder.ts` stops tracks immediately on cancellation and checks for detach/cancel after late `getUserMedia`. Reuse the lifecycle principle, not MediaRecorder or its accumulated blobs.
* `wixy_server/__main__.py` currently uses one `uvicorn.run(app, ...)` without explicit WS message/queue/compression settings. Application-level length checks alone cannot bound allocation before a WS message reaches the route.

These observations were checked in the files requested in the dossier, with `docs/ai/livechat.md`, `docs/ai/architecture.md`, `spec/README.md`, the server-chat brief, the lock model, server entry point and auth tests as supporting context.

## Exact authentication design

Add `GET /api/admin/server/calls/ws` as a WebSocket route in a dedicated route module. Browser construction is `new WebSocket(sameOriginWssUrl, "wixy-call-v1")`. URL has no query string. The subprotocol is a public protocol identifier, never a credential. Existing Cloudflare login cookies may accompany the upgrade normally; the Wixy unlock token must never enter cookies, browser storage, URLs, subprotocol headers, logs or telemetry.

1. Before accepting, require the exact configured public Origin, including scheme and port. In production it is the explicitly configured HTTPS admin/site origin; never infer trust from arbitrary Host or forwarded headers. Reject absent, `null`, duplicate or foreign Origin, query parameters, unsupported subprotocol and duplicate assertion headers. If `Sec-Fetch-Site` is present, require `same-origin`; absence alone is not a rejection because browser support differs. Local test origins are explicit and development-only.
2. Independently verify the upgrade's single `CF-Access-Jwt-Assertion` using the same `verify_access_jwt` and the same configured JWKS/audience/team values. Expose a shared verifier collaborator from `create_app`; do not invent a second JWT implementation or make a fake HTTP Request. Bound concurrent verification/JWKS work. Deny on verifier/network failure.
3. For this human calling surface require a nonempty verified `email` claim and a finite numeric `exp` in the future. Reject service-token/sub-only identities, even though ordinary admin HTTP currently permits a `sub` fallback. Bind the call's identity to the exact email string that token minting uses; no separate normalization. Require expiry explicitly: the current verifier checks an existing expiry but does not list `exp` as a required claim. Preserve the existing signature/issuer/audience/skew verification, then enforce the call's own expiry deadline. Do not trust `CF-Access-Authenticated-User-Email` in production.
4. Accept only after those checks, selecting `wixy-call-v1`. First application message, within five seconds, must be text JSON `{"type":"auth","v":1,"token":"...","label":"..."}`. It is at most 4096 UTF-8 bytes, with an at-most-2048-byte token and at-most-32-character display label. Reject binary, additional auth attempts, malformed/unknown fields and extra pre-auth commands. Until success allocate no participant ID, expose no presence, and allow no call or media actions.
5. Extract a shared async token-validation helper accepting explicit token, verified identity, secret and store. Both HTTP `require_server_token` and WS authentication use it, including the device-grant check. Keep the HTTP header contract unchanged. Discard the raw WS token after verification; retain `ServerAuth`, its expiry, and a hash only if needed for rate budgets.
6. On success issue a fresh random 128-bit connection ID and an in-memory presence entry. Send `welcome` with connection ID, protocol/media settings and the effective authorization deadline: `min(unlock expiry, Access JWT expiry)`. The client also maintains its existing session-expiry guard. No call lasts beyond either credential's deadline.
7. Recheck device-grant liveness at most every two seconds, off the event loop; stop immediately on a known local revocation notification. Fail closed if validation cannot be refreshed by its deadline. Every media receive/send checks the cached authorization deadline and current call state. Do not allow a blocked database check to leave indefinite authorization. A timer handles expiry even during silence/mute.
8. End the call and close on expiry, revocation or authentication failure; use a small fixed reason vocabulary with no tokens or user input echoed. Pre-accept refusal can use the ASGI-supported denial/close path; do not depend on browser JavaScript reading its HTTP response body. Post-accept examples: 4401 locked, 4403 forbidden, 4408 deadline, 1009 oversize. Client-originated closes use a browser-legal code such as 1000 or a defined 4xxx code.

On an unlock-session replacement during a call, the first version ends the call, closes the old WS and authenticates fresh presence with the new session. This is deliberately simple and visible; do not silently keep using old grant authorization or transfer ownership. Same-token repeated `attach` is idempotent. Re-authentication for seamless calls is a separate future protocol, not a reason to bypass expiry now.

The development bypass must mirror the existing explicitly enabled, production-forbidden setting. Tests provide a deterministic development identity; production never falls back when an assertion is absent. The browser cannot set a custom WS unlock header, which is why the first frame is needed. Do not put a token in a URL to avoid this limitation.

CF Access policy revocation cannot be discovered instantly from a previously verified signed JWT alone. Expiry and connection re-establishment are enforceable here; do not claim instantaneous external-policy revocation without an additional supported introspection mechanism. Local lock and device-grant revocation have the explicit behavior above.

## Ownership, acceptance and state protocol

One in-process `CallBroker` belongs to the FastAPI application lifespan. It holds a bounded presence table and **at most one call with exactly two immutable connection IDs**. This first version is one process per deployed site. No shared SQLite call state, no persisted SSE events, and no use of email, display name or device-grant ID as a participant address.

Each authenticated socket is a distinct participant even when two tabs use the same email or the same unlock token. Presence labels are escaped display text, not identity proof. Display a short ephemeral connection discriminator so two same-name tabs can be targeted intentionally. Other unlocked tabs may appear as available but never receive an established pair's media or detailed call state. No outside-chat ringing or notification. A third connection cannot join, replace or resume either endpoint; knowledge of a call ID conveys no permission. There is no join-by-email or bearer call-room secret. Socket membership is the authority.

State machine: `available -> ringing -> preparing -> connected -> ended`. Both endpoints are reserved atomically at invite time. All transitions run through the broker under one short state lock, with no network/database await inside it. A bounded writer per socket owns all sends. Removal, timeout and disconnect are idempotent and compare both connection and call epoch, so old cleanup cannot end a newer call.

| Direction | Message | Semantics |
|---|---|---|
| Client to server | `invite {requestId,targetConnectionId}` | Only an available source may target another available socket. Clicking Call is the caller's explicit acceptance. Server creates a random call epoch, immutable pair and 30-second ringing deadline. |
| Server to pair | `outgoing` / `incoming {callId,peer,expiresInMs}` | Incoming is delivered to precisely the target socket. All other sockets get at most an availability update. |
| Callee to server | `accept {callId}` or `decline {callId}` | Accepted only from that call's reserved callee in ringing. No broad listener, winner-by-email or answer on another device. |
| Server to pair | `prepare {callId,format}` | Both have accepted. Only now start microphone acquisition. Neither endpoint transmits or renders microphone samples yet. |
| Client to server | `ready {callId}` / `failed {callId,reason}` | Ready requires a running audio context, supported worklets and live mic tracks. Failure or a 20-second preparation timeout ends both sides. |
| Server to pair | `connected {callId}` | Sent only after both ready. The client now enables media and acquires its voiceCall idle suspension. |
| Client to server | `mute {callId,muted}` | Updates participant status; mute stops outbound sample production and discards pending samples. It does not end the call or release its idle suspension. |
| Either to server | `end {callId}` | Either member can end from any nonterminal state. Caller cancellation and callee decline are terminal. |
| Server to pair | `ended {callId,reason}` | Terminal, drops media/credits/queues/reservations. No call resume. |
| Both directions | `ping/pong`, bounded media credits/acks | Liveness and freshness, independent of speech activity; a muted call stays live. |

All post-invite actions carry the call epoch and are checked against the sending socket's membership and role. Crossing invites cannot create two calls: first serialized reservation wins, second returns busy; do not automatically turn it into consent. Reject self-calls, stale IDs, delayed accepts, replayed ready, unauthorized end/mute, duplicate differing request IDs and unnegotiated media. A bounded recent-request cache makes exact retransmissions idempotent, not a second invitation. A caller or callee that has ended cannot be resurrected by a delayed permission, ready or connected event.

An accepted invitation is not yet connected. An AudioContext may need activation during the user's Call/Accept gesture: create/resume an empty graph then, without capturing or playing audio. On `prepare`, request `getUserMedia` with mono, echoCancellation, noiseSuppression and autoGainControl preferences. Browser settings and listening tests determine what actually works. No microphone capture before both consent, no sample delivery before both ready. If activation was lost, ask for a local Enable audio gesture within the preparation deadline; do not silently remain connected with an unusable graph.

## Client lifecycle and the binding lock rule

Add a dedicated `voiceCall` suspension reason to `types.ts`; do not reuse `mediaPlaying` (which also participates in current renewal behavior) or `recording` as an unrelated owner. Obtain one release function when entering connected. Hold it during mute, remote mute, silence and brief jitter. Release exactly once on every terminal path. The existing panel hook restarts a fresh full configured idle period when the last suspension ends. Ringing alone must not keep an unattended unlocked chat open. Preparation may use the existing bounded micPermission suspension, released on timeout/cancel even if the browser permission promise never settles.

Do not add voiceCall to `isPickerOrMicOpen`, disable hidden handlers, acquire an unconditional screen wake lock, alter device-grant preferences, or force a different tab/screen policy. With hidden policy `ignore`, an unlocked call may continue if the platform keeps audio alive. With lockNow, stop immediately. With shield, existing `detachChat` ends it immediately; a later shield restore may restore chat, **never the call**. Screen-lock policy continues to decide whether an actual lock occurs; every actual lock stops the call regardless of idle suspension.

`chatView` owns a `CallController` for its attachment lifetime. Its `detach` and `dispose` call synchronous local teardown before async cleanup: invalidate generation, set terminal state, stop every track, disconnect capture and playback graphs, silence/flush the playback ring, close message ports, cancel timers and pending credits, release suspensions and close the socket. Best-effort end signaling never delays these actions. Pagehide, route departure, socket close/error, track ended, unusable audio-context state and authorization failure use the same terminal path. BFCache restoration starts fresh presence with no call.

Every await (permission, addModule, resume, auth, readiness) captures a generation and checks it before installing resources. A late stream is immediately stopped; a late AudioContext/node is immediately closed/disconnected. Late promise rejection must not clear resources belonging to a newer attempt. `getUserMedia` cannot be assumed abortable. Stale connected events cannot reacquire the idle suspension. A call auth failure tears down audio **before** `hooks.lockNow("unauthorized")`, because that hook may choose grant renewal instead of an immediate visible lock.

Calls and voice-note recording must not own the mic concurrently. Keep this arbitration inside the chat's media/controller seam: disable Call/Accept while a voice note is active and disable starting a voice note while a call is preparing/connected. Preserve already staged note data. Pause other chat audio/video on call entry to avoid competing playback; do not silently restart it at call end.

Immediate local stop means no subsequently scheduled audio after teardown, subject to the browser/device's already committed output quantum. A remote network peer cannot know about a lock instantaneously across a partition. Expiring media credits cap that residual window; never claim literally zero remote samples after an unobservable remote lock.

## Bounds and media protocol

These are proposed initial constants, not measured results. Put them in typed protocol/config modules and test boundary behavior.

| Resource | Initial bound / action |
|---|---|
| Auth/presence | At most 4 pending auth sockets and 8 authenticated sockets per site; admission work also capped before JWT verification. Per-identity admission budget 12/minute, burst 4; fixed bounded rate-table capacity. Same-email legitimate pair remains supported. |
| Authentication | Five-second first-frame timeout; verifier work has its own bounded concurrency/time budget; no unlimited orphan thread creation on cancellation. |
| WS transport | Explicitly select a supported Uvicorn WS backend with 4096-byte reassembled-message limit, receive queue 4 and compression disabled. Reject oversize/fragmented aggregate before application JSON/PCM allocation. Set and test these in the real entry point, including alternative launch paths. |
| Call lifetime | Ring 30 s; prepare 20 s; connected maximum 2 h or earlier authorization deadline. End requires fresh consent for another call. |
| Controls | JSON <=4096 bytes, label <=32 chars, fixed enums and schemas. Control budget 30/s burst 40 including acknowledgements; invitations 6/minute/connection plus site admission limits. Bounded request cache 32 entries, maximum 60 s retention. |
| PCM | Exactly 480 mono int16 samples / 20 ms / 960-byte payload; never JSON/base64 audio, floats or arbitrary sample counts. Nominal 50 frames/s; media bucket 55/s with burst 10, plus fixed byte cap. Reject sustained excess. |
| Application queues | Media queue <=5 frames per direction (100 ms), drop oldest unsent at capacity. Control queue <=16 messages; overflow terminates socket. No unbounded tasks created per frame. |
| Browser send | Check bufferedAmount before every send; cap 8192 bytes. Do not add more audio above cap. End on backlog lasting 250 ms; discard unsent capture frames. Already queued TCP data cannot be recalled. |
| Playback | Fixed ring <=200 ms; initial target 60 ms; silence on underrun, discard old samples on overflow; no catch-up playback. Bounded drift correction, never growing the ring. |
| Worklet communication | Fixed pool/credit count of at most 5 transferable capture frames and bounded playback grants. No unlimited MessagePort postMessage backlog when the main thread stalls. |
| Writer deadline | One socket writer; send timeout 250 ms. A blocked writer ends that connection and its call. End signaling has priority over queued media, which is invalidated first. |
| Liveness | Application ping/pong every 2 s; terminate after 6 s without valid response. Protocol-level ping is additional, not evidence the audio graph is alive. |
| Grant check | Refresh at most every 2 s; failed/overdue refresh revokes media permission. Absolute token/Access expiry checked independently of speech. |

`WebSocket.bufferedAmount` alone does not bound inbound browser buffering. The WebSocket API has no automatic backpressure ([MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)). Implement end-to-end credit/ack limits: at most five unacknowledged media frames per receiver, with acknowledgement only after admission to its bounded playout machinery. Stop forwarding to a receiver that has exhausted credits; end if it does not recover within 500 ms. A main-thread stall cannot therefore accumulate an entire call in browser/network queues.

Queue size and sequence numbers alone also do not prove freshness: TCP can deliver old, perfectly ordered samples late. Use short receiver-issued playout leases, expiring within 300 ms on the receiver's own monotonic timeline, and server-issued capture leases expiring within 300 ms on the server's monotonic timeline. Refresh at 100 ms while connected. The server accepts media only against a still-live capture lease and stamps a current receiver playout lease when forwarding. A receiver drops frames whose playout lease expired, even if they have only just arrived from TCP. Leases are fixed bounded records, not credentials or durable state. No synchronized wall clocks required. Receipt of any media must never extend a lease. End on sustained lease failure; do not relabel old frames as fresh.

Binary envelope: fixed version/type, call epoch (128 bits), sender sequence (uint32), capture sample index (uint64), capture lease ID and recipient playout lease ID (uint32 each), reserved bytes zero; freeze a 48-byte header and exact endian/offset layout in the implementation protocol document. Sender leaves recipient lease zero; only the broker fills it. Payload is exactly 960 bytes. The broker derives sender from the socket, never a payload-supplied identity. Validate epoch, increasing sequence/sample positions, leases, shape and rate before forwarding to the one paired receiver. Gaps are permitted for dropped audio; duplicates/backwards values and impossible jumps are rejected. Call maximum prevents sequence wrap. No payload logging.

Worklet playback must enforce lease expiry/render credits itself, not rely solely on main-thread timers. When audio/context/browser execution suspends, discard queues on resumption and require fresh leases before rendering. A stopped main thread must let the worklet's short render lease expire to silence. Browser/OS preemption cannot offer hard real-time deadlines, but resumption must never release stale audio.

Use native AudioContext rate and an actual bounded resampler to/from 24 kHz. Do not assume getUserMedia honors sampleRate, assume render blocks are always 128 samples, or play 24 kHz samples at a 48 kHz clock. [MDN's AudioWorklet sampleRate](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletGlobalScope/sampleRate) identifies the context rate. Request browser echo cancellation but do not claim it guarantees speakerphone quality. No ScriptProcessor or accumulating MediaRecorder chunks as fallback.

Explicit Uvicorn settings matter: message/queue/compression options have backend-specific support and permissive defaults. Verify installed backend behavior with real socket tests, not TestClient alone. See [Uvicorn settings](https://uvicorn.dev/settings/).

## Deployment and failure ownership

All broker operations use one application instance. A process restart terminates calls and destroys presence, leases and queued PCM. Lifespan shutdown marks the broker closed, invalidates all calls, cancels bounded workers and closes sockets. No recovery file or reconnect token. Multiple server workers would require a different coordination design and are unsupported for this version.

Blue/green overlap is a real seam: old sockets may remain attached to the old process while new sockets reach the new one. Do not pretend local-memory presence is shared. Deployment must drain/terminate existing call sockets and shut down the old broker within a bounded grace period before treating the new instance as fully active. During a transition report unavailable/ended and require a new call. Verify the actual Slots lifecycle; this review did not test it. Never add a persistent broker merely to hide this transition.

Privacy is absence of persistence, not a promise to defeat host memory inspection. Do not put PCM, auth frames, names, call IDs or captured waveforms into access/application logs, error trackers, temp files, browser storage, SSE history, backups or transcription queues. Permitted diagnostic counters are aggregate sizes, drops, timing and fixed terminal reasons; synthetic-audio validation artifacts contain no real conversation.

## Modular implementation plan

1. Freeze the endpoint, auth claims, state diagram, binary offsets, limits and lock behavior in the voice-call spec. Document that `types.ts` currently marks interfaces frozen; this review proposes the narrow voiceCall addition for the owning architect to adopt, not silent redefinition by a parcel.
2. Extract shared explicit token/grant authorization in `livechat/tokens.py`; add a shared Access-verifier seam in app setup. Keep HTTP behavior and fixtures unchanged. Implement `livechat/call_protocol.py`, `call_broker.py`, `call_limits.py` and `routes_livechat_calls.py`. Separate pure transitions/validation from async socket writers and grant checking. Wire lifespan and explicit server WS bounds.
3. Implement `admin-ui/src/server/call/{protocol,transport,controller,audio}.ts`, capture/playback worklets and a small call-controls view. Controller owns state and generation; audio module owns resources and bounded resampling; transport owns WS/auth/credits. Extend the existing build to emit self-hosted worklet assets. No framework, CDN or new global headers solely to obtain SharedArrayBuffer; bounded transferable buffers suffice.
4. Integrate only lifecycle and UI seams in chatView/thread, the new SuspendReason and microphone arbitration with the recorder. Panel remains the lock-policy owner. Add targeted teardown/idle/policy tests before UI polish.
5. Run focused broker/auth and real WS tests, TS controller/worklet tests, then the local two-browser synthetic loop. Only after it works locally perform the physical-device/production-tunnel validation below. Rebuild committed assets with LF sources, strict TS/Python checks, relevant regression suites and docs/ai contract/invariant/runbook updates. Existing private-chat release-note rule applies to any eventual commits.
6. Freeze the locally proven candidate, then perform the required independent security/concurrency audit and final PR/CI/delivery gates. This architecture review is not that implementation audit and does not certify launch.

## Acceptance and real-audio validation

Security/state tests must cover missing/duplicate/tampered/expired/wrong-audience/wrong-issuer Access assertions, email-less identities, absent expiry, forbidden/null/missing/duplicate Origin, hostile sibling subdomains, query credentials, first-frame timeout, oversized fragmented WS messages, malformed JSON/binary, unlock email mismatch, revoked grant and post-auth expiry during mute. Run production-auth tests with real signed test JWTs; a dev-bypass test cannot establish the dual gate. Assert tokens never appear in URL, logs or browser storage.

Prove a pair using the **same CF email**, including same-token sockets, can call each other while a third same-email socket cannot answer, end, replace, receive frames or resume their call. Exercise simultaneous invite, late accept, target disconnect, stale ready, stale media, stale cleanup, process shutdown, busy call and call IDs guessed/copied from another socket. Check every terminal transition destroys ownership and releases resources exactly once.

Client tests use controlled promises and clocks: lock/detach/dispose/pagehide during every asynchronous boundary; then resolve getUserMedia/addModule/resume. Every resulting track must stop, no sample may be transmitted/rendered, and no suspension may be reacquired. Include silent token renewal/grant adoption, shield/restore, audio context suspension, repeated attach and a stale old rejection arriving during a new attempt.

Binding idle acceptance: connect and remain muted longer than the configured idle period, both visible and backgrounded with policy ignore; chat stays unlocked. End the call and assert the entire newly configured idle duration elapses before idle lock (including the wall-clock return path). A second outstanding suspension keeps the timer paused. Manual panic/escape, configured hidden/screen lock, token failure and grantOff still stop the call immediately. Test shield explicitly: it ends audio; restoring chat does not restore audio. No unsolicited change to either preference.

Resource/freshness tests stall the server writer, stop reading on the receiving socket, freeze the browser main thread while its worklet runs, block permission forever, flood controls/PCM and deliver old TCP frames after a stall. Measure bounded outstanding bytes/frames/tasks and zero stale playout beyond the lease budget; confirm silence instead of delayed catch-up. Test 44.1/48 kHz capture/playback, sequence gaps and prolonged clock drift. A graph test with fake samples alone does not establish working microphones or echo cancellation.

For real-audio proof, use two physical devices, headphones first, on different networks (one cellular, one external broadband) through the actual HTTPS hostname, Cloudflare Access and tunnel. Both must deliberately Call/Accept. Test every browser/platform actually being claimed supported; include the operator's phone browser, not merely two desktop Chromium contexts. Perform at least one 15-minute duplex call with silence, mute/unmute, interruptions and ordinary simultaneous chat use. Repeat on speakers to evaluate echo and double-talk. No recording or transcription of conversation; use ephemeral counters and live listening. Synthetic chirps can measure latency without retaining human audio.

Proposed launch thresholds: ordinary-network synthetic one-way p95 mouth-to-ear <=300 ms, no delayed bursts after a forced stall, understandable double-talk without sustained feedback, no steadily growing queue/memory over the 15-minute run. Report sample counts and measurement method; this is a target, not a result. Under +100 ms round-trip delay, 30 ms jitter and 1% loss, require either intelligible audio without multi-second accumulation or a prompt explicit call failure. Do not call a long silent connection success. Verify CPU and audio underruns on the actual phone, not just the relay.

Exercise local lock and remote hangup while sound is flowing; verify tracks end, mic indicator clears, local playback stops and the other side reaches silence within the measured freshness/liveness bounds. Test real network loss and tunnel/server restart, and token/grant expiry with short test lifetimes. Reconnection must restore only availability. Test hidden/screen behavior against each configured policy; platform background termination is an explicit unsupported/ended outcome, never a promise of mobile telephone behavior.

No new operator decision is needed to implement and locally test this WSS plan. Operator input becomes necessary if it fails the actual audio gate and TURN/router exposure, paid relay, E2EE or materially different mobile/background guarantees are proposed. Until the listed evidence exists, status is **architecture selected; live calling unproven**.
